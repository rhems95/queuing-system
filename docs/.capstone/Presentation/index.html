02Background / Problem

  • PECIT Cashier, Registrar, and DMO handle student payments, records, and data transactions.
  • Clients currently wait in a manual first-come-first-served line and do not receive a queue ticket.
  • Effects: unclear order, line cutting, weak priority handling, crowding, and no shared view of who is waiting.
  • Staff cannot coordinate several windows from one organized queue.
  • PECIT needed a standalone LAN kiosk that still works when the internet is down.

The problem is not the absence of computers. Arrival order in a physical line is the only queue rule.

03Statement of the Problem

How can a standalone kiosk-based queuing management system replace first-come-first-served lining that currently uses no queue ticket with an organized, monitored, and coordinated queue at PECIT?

  1. 01Organize Cashier, Registrar, and DMO instead of a physical line with no ticket and line cutting.
  2. 02Check Student ID or authorized walk-in before a number is issued.
  3. 03Give clients a queue reference when there is no ticket, and serve priority fairly across shared windows.
  4. 04Let clients and windows see who is serving and who is waiting.
  5. 05Evaluate functionality, usability, efficiency, reliability and accuracy, and satisfaction.

04Project Objectives

General objective

Design, develop, and implement a standalone kiosk-based queuing system with a thermal printer for PECIT student service offices.

  1. 01Develop a standalone kiosk system for Cashier, Registrar, and DMO.
  2. 02Confirm with Student ID or authorized kiosk-PIN walk-in before numbering.
  3. 03Print a 58mm ticket and call 2 Priority → 1 Regular across shared windows.
  4. 04Provide a real-time public display and staff monitoring.
  5. 05Evaluate with testing, expert review, and UAT (ISO/IEC 25010-aligned).

Every later result maps back to these five. This study does not claim a measured drop in waiting time.

05Scope and Limitations

In scope

  • Users: students, walk-ins, staff, administrator
  • Offices: Cashier, Registrar, DMO
  • Modules: Kiosk, Staff, Administrator, Display
  • Platform: LAN · Laravel 12 · MySQL · 58mm XP-Q90EC
  • Cashier 1–3 share one waiting queue

Limitations

  • No online reservation, mobile app, SMS, or cloud admin
  • Not all campus offices
  • RFID/NFC is not in this build — listed as later work
  • No second student ticket while one is still in the queue
  • No claimed measured cut in waiting time

Built for PECIT Cashier, Registrar, and DMO on a local LAN — not an online reservation product.

07System Architecture

If the internet drops, the queue can still run on the local network. No cloud service is required for daily operations.

08System Development Methodology

Waterfall was used because the campus process was already defined: lock the queue rules, then build and test them.

1. RequirementsManual line, ID confirm, walk-in PIN, shared cashiers
2. DesignLAN, 58mm print, 2P→1R, Hold, number-only display
3. ImplementationLaravel 12 modules: kiosk, staff, admin, display
4. TestingFunctional tests, expert review, UAT
5. DeploymentStandalone XAMPP / LAN at PECIT offices

Four modules: Student Kiosk · Staff · Administrator · Queue Display.

09Major System Features

Hold is not Complete. Guard cannot log in. Names stay off the ticket and the public display.

10Technology Stack

Languages / frameworkPHP 8.2+ · Laravel 12 · Blade
FrontendVite · Tailwind · local fonts and icons (no CDN)
DatabaseMySQL / MariaDB · queuing_system

Laravel keeps queue rules on the server (fair claim, one open student ticket, PIN check). Local assets keep the kiosk usable offline.

11Testing and Evaluation

  • Chapter 3 survey (N = 50): students and parents rated the current line before development. Not mixed with Chapter 4.
  • Chapter 4 evaluation: functional tests, office UAT, student system form, and one IT expert.
  • Form: ISO/IEC 25010 is the basis of the evaluation form only — not a certification.
  • IT expert: same five areas, 25 items; overall 5.00; not mixed into the user table.
  • Student form: 20 students, 5 parents, 5 walk-in visitors (N = 30).

Efficiency is a perception score, not a measured cut in waiting time.

14Conclusion

  1. 01A standalone kiosk can replace the manual line at the selected offices.
  2. 02Confirmation (Student ID or PIN walk-in) works before numbering.
  3. 03The ticket is a clear reference; 2 Priority → 1 Regular is fair on shared windows.
  4. 04Display and staff panel give a real-time number-only view.
  5. 05Users 4.96 and IT expert 5.00 support acceptance under ISO/IEC 25010-aligned items.

A practical replacement for the manual line. No claimed measured cut in waiting time.

15Recommendations / Future Enhancements

Now (implemented)

  • Deploy kiosk, printer, display, staff PCs, and LAN as specified.
  • Before go-live, prepare network setup for PECIT’s cloud-based network.
  • Orient staff on Confirm errors, walk-in PIN, Hold, and Call Held.
  • Keep the student allowlist and PIN current; back up MySQL.
  • Use done-only reports; do not treat Hold as Complete.

Later (not built)

  • Modernize staff and kiosk UI; keep the 3-step kiosk and number-only print and display.
  • Record actual wait and service times if PECIT wants a measured comparison.
  • RFID/NFC tap at confirm — still number-only on print and display.
  • Optional SMS / QR status — still no names on print or display.
  • Remote reserve would still require ID or authorized walk-in.
  • More offices only if they share the same local rules.
